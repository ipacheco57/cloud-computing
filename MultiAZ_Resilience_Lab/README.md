Recovery Time

So during the tests, the Uploader took 89.1 seconds to recover while the Viewer took 78.9 seconds, so both were able to meet the 180-second SLO that was set. However, once I tested the Uploader again with a 60-second SLO, it took 89.4 seconds and failed that requirement. I would say the main reason recovery took this long was because there was only one instance running for each application, meaning there wasn't another one already available when it failed. Instead, the Auto Scaling Group had to launch a replacement instance, which also needed time to install and start the application. The ALB then had to recognize the new instance as healthy, and since the health checks were running every 10 seconds, that could add some additional time before traffic was directed to it. I think this shows that most of the recovery time was likely spent getting the replacement instance ready rather than the ALB itself taking a long time to redirect traffic.


Changes 

I think the main difference from the previous lab was that instead of using run-instances to directly launch the Uploader and Viewer, I changed create_app_stack.sh to use Auto Scaling Groups. Before, if one of our EC2 instances failed, we would have to launch another one ourselves, but now the ASG can automatically replace it using the Launch Template. I also added an ALB to direct traffic to healthy instances rather than accessing them through their individual public IP addresses. Something I initially misunderstood was whether the ALB was responsible for replacing failed instances, but I learned that it only handles the traffic while the ASG handles the replacement. As for delete_app_stack.sh, I had to update it to remove the additional resources in the right order, since some of them depended on each other.
